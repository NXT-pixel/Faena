# Task List Management (Faena TDD)

## Scope

- Applies to `tasks/task-<ticket>/task01-setup-*.md`, `taskNN-red-*.md` and `taskNN-green-*.md`.
- These files are generated by `@commands/3-create-tasks.md` from the TRD task breakdown. The TRD is the authoritative source: never add, reorder or rename tasks on your own.
- Does **not** apply to `tasks/context/**`, `design-*.md`, `trd-*.md` or `test-spec-*.md`.

## Execution Order

`task01-setup` -> `taskNN-red` -> `taskNN-green` (+ VERIFY).

A GREEN file never starts before its RED file has failed **for the expected reason**.

## Per-File Protocol

1. Read the TRD and the test spec in the same folder.
2. Read the folder's `README.md` and locate its **Quality Gates** section: that is where the real commands for this repository live.
3. Work the file's sub-tasks in order: X.1 test -> X.2 implementation -> X.3 quality gate.
4. Run all tests and gates inside the client repo (`Proyecto/<repo>/` or `tenants/<tenant>/Proyecto/<repo>/` per `.active-tenant` in `PROTOCOL.md` §1), never from the harness root.
5. Mark `[x]` in the folder `README.md` **and** in the task file, then update `todo_write`.
6. Report the result and stop: one task file per turn in manual step-by-step mode. In autonomous mode (`@commands/orchestrate.md`), mark the task complete and immediately proceed to the next unchecked task in `README.md` until all tasks are finished.

## TDD Sub-Task Pattern (X.1 -> X.2 -> X.3)

### X.1 - RED (write the test)

- Write the test first, following the test spec (Given-When-Then) and the naming/arrangement conventions of the repo.
- Run only that test (e.g. `dotnet test <Tests.csproj> --filter "FullyQualifiedName~MyTest"`, `npx jest <path>`, `pytest <path>`).
- It MUST fail, and it must fail for the right reason: missing behavior, not a typo, a broken import in the test harness or a compile error in production code you were not asked to touch.
- If it passes immediately, the test does not exercise the requirement: fix the test, never weaken the requirement.
- Record the failing output in the task file or in your report. Without that output the RED phase did not happen.

### X.2 - GREEN (minimum implementation)

- Implement only what the failing test needs, respecting the architecture in the TRD.
- Re-run the task's tests, then every test that depends on the code you touched (previous tasks included). Dependent tests may still fail only if they depend on a future task - never because of missing current code.
- Run the `verify:quick` gate defined in the folder `README.md`.

### X.3 - VERIFY (quality gate)

- Run the `verify` gate; run `verify:full` for the final task or before an integration handoff.
- For frontend work also run the build/lint the README specifies (e.g. `yarn build`, `ng build`).
- Only then mark the task complete.

## Quality Gates Are Project-Defined, Never Assumed

Faena projects differ (.NET/ABP, Angular, Node, Python). The commands always come from the ticket folder's `README.md`, in the **Quality Gates** section:

| Gate | Intent | Example (ABP / .NET) |
| :--- | :--- | :--- |
| `verify:quick` | targeted tests for the feature | `dotnet test services/core/<Service>.Tests --filter "FullyQualifiedName~Feature"` |
| `verify` | full suite of the affected service | `dotnet test services/core/<Service>.Tests` |
| `verify:full` | build + full suite (final integration) | `dotnet build services/core/<Service> && dotnet test services/core/<Service>.Tests` |

Rules:

- Use exactly the command written in the README; do not substitute a weaker or partial one.
- If the command does not exist in the repository (missing script, target or test project), **STOP** and report the mismatch. Do not invent `npm run ...`, `yarn ...` or `dotnet ...` gates that the repo does not define.
- Never skip a gate because it is slow or because "the change is small".

## Prohibitions

- Never write implementation before a failing test exists for it.
- Never delete, weaken or disable a test to obtain a green run (`skip`, `[Fact(Skip=...)]`, `pytest.mark.skip`, `it.skip`, `.only`).
- Never mark `[x]` without having run the gate and without pasting its result.
- Never silence a failing dependent test.
- Never leave secrets, debug prints, commented-out code or TODOs in the diff.
- Never `git commit` or `git push` inside `Proyecto/<repo>` without the corporate identity check described in `rules/project/` and `tasks/context/team-context.md`.

## When Tests Disagree (Pause and Report)

Stop and ask for guidance instead of editing tests silently when:

1. Tests contradict each other or expect an impossible state.
2. Test expectations do not match the schema, DTO or type definitions.
3. Tests expect a pattern that violates the architecture in the TRD.
4. Critical behavior or validations are not covered and the test spec missed them.
5. Mock/fixture data violates domain constraints or shares mutable state between tests.
6. The expectation can only hold with timing/async tricks that cannot be guaranteed.
7. Test setup is brittle or depends on execution order.

## Completion Checklist (Before Reporting a Task as Done)

- [ ] RED output recorded, failing for the right reason.
- [ ] Task tests pass, plus dependent tests.
- [ ] Quality gate from the folder `README.md` passed, output pasted.
- [ ] `[x]` marked in the task file AND in the folder `README.md`.
- [ ] Every file created/modified listed (task's "Relevant Files" section).
- [ ] No secrets, no debug leftovers, no skipped tests.

## Recovery

If a task was marked `[x]` without the gate, or a checkbox was updated in only one of the two files: revert it to `[ ]`, state the oversight, run the missing gate, and only then mark it again.
